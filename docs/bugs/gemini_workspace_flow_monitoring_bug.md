# Gemini Workspace Flow Monitoring Bug

Date observed: 2026-05-24

## Summary

During a monitored headless Gemini CLI run for `workspaces/Healthcare-RCM-Data-Platform`, Gemini displayed the workspace-selection panel reasonably well, but it did not reliably use the deterministic project tools required by `AGENTS.md`.

The main bug is that Gemini can produce plausible workflow text while its actual tool environment cannot run the required repo commands. In that state it may either:

- fall back to memory/context instead of executing the required command;
- manually simulate panels that should be generated by deterministic tools;
- invent an unverified scope-enforcement file such as `interns/state/workspace_settings.json`.

This makes the CLI response look correct while the governed workflow has not actually advanced.

## Reproduction

Run Gemini headlessly from the repo root:

```powershell
gemini --skip-trust --session-id <id> --output-format stream-json -p "<workspace setup prompt>"
```

Prompts used during the observed session:

1. Ask Gemini to perform Step 0 for `workspaces/Healthcare-RCM-Data-Platform`.
2. Confirm scope: use only EMR Hospital A.
3. Select Option 2: usual workflow / onboard existing KPI + data model.

Observed monitor logs:

```text
state/gemini_monitor/dc4589e8-21e3-4909-abd6-7318519c7b4a.stream.jsonl
state/gemini_monitor/dc4589e8-21e3-4909-abd6-7318519c7b4a.workspace_select.stream.jsonl
state/gemini_monitor/dc4589e8-21e3-4909-abd6-7318519c7b4a.hospital_a_scope.stream.jsonl
state/gemini_monitor/dc4589e8-21e3-4909-abd6-7318519c7b4a.option2_usual_workflow.stream.jsonl
```

## Expected Behavior

For workspace selection:

- Use `uv run list-workspace-files --workspace workspaces/Healthcare-RCM-Data-Platform`, or a bounded fallback with gitignore disabled when shell execution is unavailable.
- Show the full active file-set panel in chat.
- Stop and ask for confirmation.

After the user confirms Hospital A scope:

- Preserve the active scope exactly:
  - `docs/Sample KPI.xlsx`
  - `docs/DataModel.png`
  - `datasets/EMR/trendytech-hospital-a/*`
- Exclude Hospital B, claims, and CPT code datasets unless the user expands scope.
- Show the two-path KPI generation panel from the deterministic tool:

```powershell
uv run prepare-kpi-generation --workspace workspaces/Healthcare-RCM-Data-Platform
```

After the user selects usual workflow:

- Run the deterministic onboarding command, or stop if shell execution is unavailable:

```powershell
uv run onboard-workspace --workspace workspaces/Healthcare-RCM-Data-Platform
```

The CLI must not invent artifacts, simulate generated panels, or claim unsupported config files.

## Actual Behavior

Good behavior observed:

- Gemini showed the full workspace file-set panel in chat.
- Gemini preserved Hospital A-only scope in prose.
- Gemini stopped when command execution was unavailable instead of simulating onboarding.

Incorrect behavior observed:

- Gemini attempted to call `run_shell_command`, but that tool was not registered.
- On a later workspace-selection run, Gemini reused previous context and made no tool calls.
- Gemini manually wrote a KPI route panel instead of running `uv run prepare-kpi-generation`.
- Gemini repeatedly claimed a required `interns/state/workspace_settings.json` / `dataset_allowlist` mechanism without proving that this is a supported repo contract.

## Impact

This creates a false sense of workflow progress. The user may see a plausible panel and next command, but the repo has not produced the expected artifacts.

Specific risks:

- onboarding may proceed with the wrong data scope;
- generated artifacts may not match deterministic project contracts;
- later KPI SQL generation can appear valid while missing source-truth requirements;
- agents may trust invented scope settings that validators do not enforce.

## Root Cause

The headless Gemini environment did not expose the shell command tool required for this repo workflow. Gemini then relied on fallback reasoning and prior context.

There is also no hard harness check in the Gemini monitoring path that fails when:

- required project commands are not called;
- source panels are manually simulated;
- unverified config files are claimed as required;
- chat output hides the full panel behind artifact paths.

## Fix Plan

1. Add a Gemini monitor harness that validates stream-json logs.

   Required checks:

   - Step 0 must include either `uv run list-workspace-files` or an explicit bounded fallback tool call.
   - Post-confirmation KPI route must call `uv run prepare-kpi-generation`.
   - Usual workflow must call `uv run onboard-workspace` or stop with a tooling blocker.
   - Responses must not mention unsupported files such as `workspace_settings.json` unless repo code/docs prove them.
   - User-facing output must include the full panel content, not only artifact paths.

2. Teach Gemini prompts to treat unavailable shell execution as a hard blocker.

   Required wording:

   ```text
   If shell execution is unavailable, stop. Do not manually simulate project-tool output.
   ```

3. Add an allowlist/scope contract only if the repo actually supports it.

   If Hospital A-only scoping needs a persistent artifact, implement and document it in repo code first. Then validators should enforce it. Until then, scope must be enforced by deterministic tool input selection and generated profile/input inventory checks.

4. Add validation after onboarding to confirm data scope.

   The validator should fail if generated workspace inventory includes:

   - `datasets/EMR/trendytech-hospital-b/*`
   - `datasets/claims/*`
   - `datasets/cptcodes/*`

   when the accepted user scope is Hospital A EMR only.

5. Keep chat display and artifact display aligned.

   The CLI should print the full current panel markdown to stdout by default and reserve JSON summaries for an explicit `--json` mode.

## Acceptance Criteria

- A monitored Gemini run cannot pass if it skips required deterministic commands.
- A monitored Gemini run cannot pass if it invents unsupported scope files.
- The workspace-selection panel is visible in chat.
- The KPI generation route panel is visible in chat.
- The KPI resolution review panel is visible in chat.
- Hospital A-only scope is preserved in generated inventory and validated before KPI mapping or SQL generation.
