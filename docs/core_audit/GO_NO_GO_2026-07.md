# Go / No-Go: AutoResearch Platform Launch

**Recommendation: GO** for the data-platform launch to data teams. Conditional GO for enterprise teams (one operational gate, below).

## What was assessed
A forced, evidence-based code audit of the full platform — onboarding → KPI generation → dashboard → medallion/Databricks deploy (~85 CLI commands). Every finding below is backed by code, not description. The audit twice caught and corrected its own false leads, and surfaced three real gaps that are now fixed and verified.

## Headline
The platform itself is in good shape and ready to ship. What blocked launch was not the platform — it was two contained issues riding alongside it: an experimental autonomous-mutation subsystem sharing the shipped container, and enterprise-credential redaction that had been built and tested but never actually switched on. Both are now resolved and verified green.

## The two blockers — resolved

**1. Ungated autonomous mutation loop (P0.1).** An experimental self-optimization subsystem — not part of the platform, from the project's original identity — wrote AI-generated code to disk unattended by default, and was the container's default startup command. It was reachable through a normal, already-shipped onboarding command. *Fixed:* the loop now defaults to safe (dry-run), refuses to write without an explicit human flag *and* an explicit environment variable, and the container's default command is now a read-only health check. A routine onboarding call can no longer arm it. Verified by 8 new tests.

**2. Enterprise credential redaction was dead code (P0.2).** The tested redaction filter that would scrub Databricks tokens and keys from logs was never actually wired in — two weaker ad-hoc versions did the real work and missed tokens appearing mid-sentence in error messages. Notably, a *prior* internal audit had analyzed this filter's coverage while assuming it was live; it wasn't. *Fixed:* the tested redactor is now wired into the shared config path every entrypoint uses, with a loud startup assertion so it can't silently regress again; the two ad-hoc versions now delegate to it; and the Databricks client scrubs tokens at the source. TDD also surfaced a real gap in the shared redactor itself (CLI-flag-style secrets, the exact shape Databricks SDK errors produce), now closed. Verified by 11 new tests.

## Verification
Full suite green after both fixes — 802 tests, zero failures, zero load errors — plus 19 new tests across the touched files. Both acceptance criteria independently confirmed: a fresh container cannot mutate without an explicit human flag; a token embedded mid-sentence in an error cannot reach the trajectory log, a session snapshot, or a client return value.

## Backlog (not launch-gating)
Coverage tooling (currently no coverage number), a duplicated dispatch table, one low-risk swallowed exception, and two open scoping questions the audit honestly flagged rather than guessed (whether `scikit-learn`/`shap` are live dependencies or vestigial; confirming the deck/press vendor trees are in-scope).

## One structural note for owners
The redaction gap is the lesson worth internalizing: "built and tested" was mistaken for "live" — by a prior audit, no less. The fix included a startup assertion so it can't happen silently again. Worth applying that pattern elsewhere: a safety mechanism that isn't asserted-live is a safety mechanism you're only assuming you have.
