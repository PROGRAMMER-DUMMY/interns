# medallion-A (design/model/build/schema) — audit

## Purpose
This half of `core/medallion/` turns governed onboarding artifacts (domain_model, kpi_registry,
kpi_feature_mapping, profiles, semantic_contract, derived_feature_reviews) into a medallion design
(`manifest.yaml`, `star_schema.json`, `silver_contract.json`, `lineage.json` + paired `.md`) and
then executes that design Bronze→Silver→Gold on a DuckDB target (with a Delta/Databricks fast path
that falls back to DuckDB). It also contains the P4 "model routing" subsystem: discover available
models, classify them via cached WebSearch, rank them into tiers, and pick a tier per task class.
Design is idempotent on `inputs_hash`; build is fingerprint-incremental, lock-guarded, and routes
stage errors through the Governor. An LLM "Medallion Architect" intern proposes the schema; a
deterministic seed proposal is the fallback so a runnable Bronze layer is always produced.

## Findings
| Tag | Location (file:line) | Description | Suggested fix |
| --- | --- | --- | --- |
| [BUG] | build.py:652-672 (`_execute_kpi_regen`) | The promised "regenerate KPI SQL against Gold" never happens. When `v2` (target_file) is missing it is created by byte-copying `v1` (row_equality_check_against), then the row-equality check compares v1 vs v2 — identical by construction, so the first run is always "equal" and no KPI SQL is ever rebuilt against the Gold tables. The docstring/module header overstate what is implemented. | Either implement actual KPI SQL regeneration (rewrite source-table refs to `gold.*`) before the equality check, or drop the copy and skip the check when v2 is absent, and correct the docstrings. |
| [BUG] | build.py:792-808 (`_run_assertions`) | On assertion-statement execution failure the except block writes synthetic keys `assertion_execution_failed_N` / `assertion_error_N` into the results dict. These keys don't start with `FAIL`, so the failing-detector at build.py:513 (`v.startswith("FAIL")`) never flags them — a SQL assertion that errors out is silently treated as non-failing. The second key stores `int(bool(str(exc)))` (always 1), which is meaningless. | Record a failure as `"<assertion_id>": "FAIL:exec_error"` (or raise), so an un-runnable assertion surfaces as a Silver failure instead of passing. |
| [BUG] | design.py:632 vs silver_contract.py:221 | Asymmetric `NullPolicy` parsing. `_build_silver_contract` does `NullPolicy.from_str(str(v))`, but `TableContract.from_dict` does `NullPolicy.from_str(v)` with no `str()`. A non-string JSON null-policy value (e.g. a dict/number from the LLM) stringifies in one path and passes raw in the other, and `NullPolicy.policy` is never validated against the documented set (`drop`/`error`/`default:<v>`). | Add a single validating `NullPolicy.from_value()` used by both call sites; reject/normalize unknown policies. |
| [NOT-PROD] | design.py:884-916 (`_emit_silver_sql_duckdb`) | The emitted Silver SQL is the documented P0 placeholder: it hard-codes `TODO(P1): apply type casts` and `TODO(P1): apply null policies` as comments and emits none of the `type_casts`/`null_policies` declared in the contract. `merge_emitter` (build) only adds MERGE semantics, not casts/nulls, so contract-declared casts and null policies are never enforced in any executed SQL. | Generate cast expressions and null-policy handling (drop/error/default) from `TableContract` into the Silver SELECT before this is called production-ready; until then the contract's casts/nulls are decorative. |
| [BUG] | design.py:881-882, 919-920 (`_source_system_from_silver_src`) | Per-source `source_system` in the Silver UNION is derived by splitting the `derived_from` string on `__` (`source_system_from_silver_source`). But `derived_from` entries are `bronze.<logical>__<source_system>` and a Bronze table with no detected source system is named just `<logical>` (design.py:670), so its UNION branch labels every row `source_system='default'`. Combined with the composite PK `["source_system","<logical>_id"]`, multi-file single-source datasets all collapse onto `default`, risking PK collisions across distinct files. | Carry the resolved `source_system` on `SilverTable`/manifest rather than re-parsing the FQN string, and ensure single-source Bronze still records its real source system. |
| [NOT-PROD] | build.py:811-824 (`_split_statements`) | Statement splitting is naive `sql.split(";")`. Any semicolon inside a string literal, derived-column formula, or `read_csv_auto` option string will split a statement mid-query. Gold/derived SQL coming from LLM templates can easily contain `;`. | Use a real SQL statement splitter (or DuckDB's multi-statement execution) that respects quotes/comments. |
| [BUG] | build.py:296-297 | On a missing Delta script, `state.per_table_status[key]` is set to `failed` and then `_route(..., fatal=True)` raises `MedallionBuildExit` immediately — even when `_strict_databricks` is false. Everywhere else a non-strict Delta failure degrades to DuckDB; a missing `.spark.py` should arguably also degrade rather than hard-abort the whole build. | Gate the fatal route on strict mode; otherwise set `degraded_run` and `return False` like the execution-failure path. |
| [BUG] | tier_router.py:59-63 (`assign_tiers`, n==2) | With exactly two ranked models, `by_tier` = `{heavy:[r0], medium:[r0], light:[r1]}`. `pick_model` for a `medium`-minimum task class returns `medium`→`r0`; fine. But there is no model that is *only* light-capable promoted to medium when needed — and for n==2 the weakest model (r1) can be selected for a `light` task that the design pipeline marks `silver_transform_sql=light`, which may be the un-classified `confidence=0.0` fallback model. Capability floors are never checked against `TASK_MINIMUMS`; tiers are pure rank buckets, so an all-zero-confidence model set still "satisfies" a `medium` task. | Add an absolute capability floor (min benchmark/param/context) per tier, not just relative ranking, before `pick_model` returns. |
| [DEAD] | budget.py (whole module) | `BudgetTracker`/`BudgetExceeded` are never instantiated in design.py or build.py (grep: only `tests/test_medallion_p2_p3.py`). `EXIT_BUDGET_EXCEEDED` is declared (design.py:74), imported and mapped to exit code 7 (design_cli.py:26,205), and documented in `_EPILOG`, but nothing ever raises it. The "BUDGET_EXCEEDED max_usd_per_run hit mid-run" CLI contract is unimplemented. | Wire `BudgetTracker.check()` into the LLM proposal path (`_build_proposal`/`_prepare_model_routing`) and raise `MedallionExit(EXIT_BUDGET_EXCEEDED, …)`, or remove the dead exit code and help text. |
| [DEAD] | prompt_strategies.py (whole module) | `strategy_for_tier`, `corrective_prompt`, `_heavy/medium/light` decomposition, `cache_key`, and `STRATEGY_VERSION` have no production caller (grep shows references only within the file itself; the selected tier from `_prepare_model_routing` is written to metadata but never used to drive prompts). The architect intern is invoked as a single `intern.design(inputs)` (design.py:372) ignoring tier strategies entirely. | Either route `intern.design` through `strategy_for_tier(selected_tier)` or delete the module; currently the entire P4 tier→prompt machinery is decorative. |
| [INTEGRATION] | design.py:457 ("…-p4" run dir) & build.py:228 | `_prepare_model_routing` selects a tier/model and writes `discovered_models_latest.json`, but the result is discarded — `_build_proposal` does not receive the selected model/tier and the intern is constructed in the CLI (design_cli.py:127) without it. So model discovery/classification/ranking runs every non-cheap design but does not influence which model actually generates the schema. | Thread `selected_model`/`selected_tier` into `_build_proposal`→intern, or mark the routing as advisory-only in docs. |
| [NOT-PROD] | model_discovery.py:76 | Gemini API key is interpolated into the request URL query string (`?key={api_key}`). URLs land in logs, proxies, and exception traces, leaking the secret. (Repo policy treats secret display as a hard stop.) | Send the key via the `x-goog-api-key` header instead of the query string. |
| [BUG] | model_classifier.py:108-109 (`_expired`) | `datetime.fromisoformat(classified_at)` yields a naive datetime if the stored string has no offset, then it's subtracted from `datetime.now(timezone.utc)` (aware) → `TypeError`, caught by the broad `except` and treated as expired. Cache entries written by `_search_and_extract` use `isoformat()` of an aware datetime so this works for self-written entries, but any externally seeded/naive entry silently never caches. | Normalize to UTC-aware on read (`if ts.tzinfo is None: ts = ts.replace(tzinfo=timezone.utc)`). |
| [BUG] | model_discovery.py:102-108 (`_looks_like_model_id`) | Discovery parser takes the first whitespace token of every non-empty stdout line and accepts it as a model id if it merely contains a `-` and len>8, or `/` and len>5. CLI banners, help text, and table separators (e.g. `------------`) are easily misclassified as models, polluting the ranked set with garbage `model_id`s that then get `confidence=0.0` capabilities and can be picked. | Constrain to known per-engine output shapes (anchored regex) or require an explicit prefix from `prefixes`; drop the loose `-`/`/` heuristics. |
| [NOT-PROD] | design.py:884-911 PII hashing | Silver PII hash uses `sha256(coalesce(cast(col AS VARCHAR),'') || $salt)`. The Bronze layer (design.py:855-864) already materialized the raw PII columns into `bronze.<table>` with `SELECT *`, so cleartext PII persists in the local `workspace.duckdb`/Delta Bronze tables; only Silver is hashed. This may violate the PHI/redaction posture the platform claims. | Confirm intended (Bronze-cleartext) policy; if not, mask at Bronze ingest or restrict Bronze persistence. |
| [BUG] | build.py:749-765 (`_check_design_panel`) | Build treats a design item as unconfirmed when `not e.get("confirmed", False)`, but `_write_design_panel` (design.py:961-968) emits panel items with only `{id, kind}` and no `confirmed` key. So every freshly written design panel makes `build` raise `DESIGN_BLOCKERS` until something external injects `confirmed:true` into `current.json`. The confirm-write path is not in this half; if no such writer exists, the gate is permanently closed without `--force-with-blockers`. | Define and document the panel-confirmation contract (who writes `confirmed`), and have `_write_design_panel` emit `confirmed:false` explicitly so the schema is self-describing. |
| [BUG] | build.py:160 (`mlflow_start`) | `_run_build` calls `mlflow_start(...)` unconditionally before the layer loop, but the early Delta success path (build.py:184-191) calls `mlflow_finalize`; the Delta *fallback-to-duckdb* path continues and finalizes later — fine. However if `_execute_delta_or_mark_degraded` raises (e.g. fatal route at :320), `mlflow_finalize` is never called and the started MLflow run is left dangling (no try/finally around the run lifecycle). | Wrap the run body in try/finally so `mlflow_finalize` always runs, or start MLflow after the Delta decision. |
| [DUP] | design.py:586-601 | Thin pass-through wrappers (`_dataset_name_key`, `_logical_entity_from_path`, `_source_system_from_path`, `_detect_natural_key`, `_detect_watermark`, `_safe_relative_posix`, `_source_system_from_silver_src`) each just call the identically-named `design_naming` function. Harmless but adds an indirection layer and two names per concept. | Import the `design_naming` functions directly where used, or keep wrappers only where a default arg differs. |
| [NOT-PROD] | incremental.py:295-308 (`_resolve_upstream`) | Unresolvable upstream deps map to the constant `_UNRESOLVED`. Correct for stability, but it means a Silver/Gold table whose upstream name never matches a planned table will be considered "unchanged" forever (after first build) even if that upstream truly changes under a different name — a silent staleness risk for mis-named `derived_from`. | Log/warn on `_UNRESOLVED` resolution so mis-wired lineage is visible rather than silently skipped. |
| [NOT-PROD] | design.py:594-600 (`_silver_host_for_inputs`) | Substring match (`name in ds`) assigns a confirmed derived column to the first Silver table whose logical name appears anywhere in the input dataset string. Short logical names (e.g. `pa` for `patient` after plural strip) can match the wrong host table; on no match it silently defaults to `silver_table_names[0]`. | Match on resolved logical-entity equality, not substring; on no match skip/flag rather than defaulting to table[0]. |

## Cross-package coupling
- Imports the lineage/emit half (sibling scope) heavily: `manifest.py` (`Manifest`, `compute_inputs_hash`,
  `manifest_to_yaml`), `delta_emitter` (`emit_*_spark`, `emit_gold_duckdb`), `merge_emitter`
  (`emit_silver_merge`), `sql_lineage_parser`/`spark_lineage_parser`, `mlflow_emit`
  (`start_run`/`finalize_run`/`write_lineage_with_runtime`), `salt_store.get_workspace_salt`,
  `run_state` (lock + `RunState`), `sql_lint.lint_sql`, `databricks_target`, `lineage.py`. Build
  correctness depends on these — e.g. the cast/null TODO can only be closed by the emitters.
- `core.orchestration.governor.Governor` — all build stage errors route through
  `decide_medallion_routing`; a `_NullGovernor` stub is used when no cfg (e.g. `--cheap`).
- `core.resource.manager` (`ResourceManager`/`ResourceDecision`) — build_cli runs a resource preflight;
  a `blocked` decision aborts local builds.
- `core.storage.workspace_layout.WorkspaceLayout` — all input/output path resolution.
- `core.agents.registry.InternRegistry` — design_cli constructs the `medallion_architect` intern.
- `core.execution.backend._strict_databricks` — gates fatal vs degraded on Delta failures.
- `core.paths.project_path` — model_classifier cache lives in `core/agents/state/`, *outside* the
  workspace tree (shared cross-workspace cache; intentional but worth noting for isolation).
- P4 routing (`model_discovery`/`model_classifier`/`tier_router`/`prompt_strategies`/`budget`) is
  largely self-contained and currently does **not** feed back into the actual LLM proposal call — a
  significant integration gap (see [INTEGRATION]/[DEAD] above).

## Verdict
The deterministic path (seed proposal → Bronze ingest → Silver union/dedup/PII-hash → Gold full
refresh → assertions → fingerprint-incremental rebuild → run-state) is well-structured, idempotent,
lock-guarded, and close to production-ready for the DuckDB target. The dataclass contracts and MD
renderers are clean. However it is **not yet production-ready** for the full advertised contract:
(1) contract-declared type casts and null policies are emitted only as `TODO` comments and never
enforced; (2) KPI regeneration is a no-op self-comparison; (3) assertion-execution errors pass
silently; (4) the entire P4 model-routing / budget / prompt-strategy subsystem is wired up to
metadata but does not influence generation and the budget cap can never trip — large [DEAD]/
[INTEGRATION] surface; (5) naive `;` statement splitting and substring-based host/source matching are
fragile on real LLM-generated SQL; (6) a Gemini API key is placed in a URL query string. Tag counts:
[BUG] 9, [NOT-PROD] 6, [DEAD] 2, [INTEGRATION] 1, [DUP] 1, [MISSING] 0. Recommend closing the
cast/null and assertion-error bugs and either wiring or deleting the P4 budget/prompt machinery before
calling this layer GA.
